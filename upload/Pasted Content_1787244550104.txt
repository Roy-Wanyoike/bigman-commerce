For this platform, I would structure the product into **four distinct experiences**:

1. **Super Admin Portal** — platform owner/operator
2. **DCP Admin Portal** — lender organization management
3. **DCP Staff Portal** — daily lending operations
4. **Customer Portal/App** — borrower self-service

The key is that **Super Admin controls the platform**, while each DCP controls its own lending business.

This is extremely important.

```text
SUPER ADMIN
│
├── Platform Admin
├── Finance Admin
├── Risk Admin
├── Compliance Admin
├── Support Admin
└── Operations Admin


DCP
│
├── DCP OWNER
│
├── DCP ADMIN
│

├── CREDIT OFFICER
├── LOAN OFFICER
├── COLLECTIONS MANAGER
├── COLLECTIONS OFFICER
├── FINANCE OFFICER
├── COMPLIANCE OFFICER
└── SUPPORT AGENT


CUSTOMER
└── CUSTOMER
```

But don't stop at roles.

Use **RBAC + ABAC**.

For example:

```text
Credit Officer

Can approve loans
BUT

loan.amount <= officer.approval_limit
AND
loan.tenant_id = officer.tenant_id
```

That becomes much safer.

# One architecture decision I'd strongly recommend

Don't think of these as four completely separate applications.

Think of them as **four surfaces on one Digital Lending OS**:

```text
                  LENDING OS
                       │
        ┌──────────────┼──────────────┐
        │              │              │
        ▼              ▼              ▼
   SUPER ADMIN       DCP              CUSTOMER
      PORTAL        PORTAL              APP
                       │
                 DCP STAFF
                  WORKSPACE
                       │
                       ▼
                  CORE ENGINE
                       │
       ┌───────────────┼────────────────┐
       ▼               ▼                ▼
     Loans          Payments           Risk
       │               │                │
       └───────────────┼────────────────┘
                       ▼
                 Temporal/NATS
                       │
       ┌───────────────┼───────────────┐
       ▼               ▼               ▼
    KYC/CRB         M-Pesa          Messaging
```

### The killer feature

I would make the **Super Admin portal an actual platform operating system**, not just another dashboard.

It should answer:

> **"What is happening across every lender, every loan, every payment, every workflow and every external provider right now?"**

And the DCP portal should answer:

> **"What is happening inside my lending business?"**

While the customer portal answers:

> **"What do I owe, what can I borrow, and what do I need to do next?"**

That separation will make the product much easier to scale to many DCPs while keeping the UX clean.
Yes. I researched this from **Kenyan DCP regulatory requirements, lending/credit operations, collections roles, and established loan-management dashboard patterns**. The biggest correction I would make to the earlier design is:

> **Do not give every DCP employee the same dashboard with different buttons. Build different workspaces around what each role is accountable for.**

CBK's DCP framework specifically covers licensing/governance, credit operations, consumer protection, credit information sharing and AML/CFT. It also requires transaction receipts/statements and a complaints-redress mechanism, while placing restrictions on abusive collection practices. ([Central Bank of Kenya][1])

Oracle's lending platform documentation also explicitly separates dashboards for **Loan Officer, Loan Authorizer, Loan Supervisor, Branch Manager and Relationship Manager**, which supports using role-specific workspaces rather than one generic dashboard. ([Oracle Docs][2])

# 1. The platform should have 5 UI layers

I would actually expand your original four into **five**:

| Portal                      | User                             | Primary purpose                          |
| --------------------------- | -------------------------------- | ---------------------------------------- |
| **Platform Control Center** | Super Admin                      | Operate the entire lending platform      |
| **DCP Administration**      | DCP Admin                        | Configure and govern one DCP             |
| **Management Workspace**    | DCP Manager                      | Monitor teams, portfolio and performance |
| **Operations Workspace**    | Loan/Credit/Collections Officers | Execute daily lending work               |
| **Customer App/Portal**     | Borrower                         | Apply, borrow, repay and get support     |

This distinction is important.

A **DCP Admin** should not see the same thing as a **Loan Manager**, and a **Loan Manager** shouldn't see the same thing as a **Loan Officer**.

# 2. Where does the money actually come from?

Suppose DCP A wants to lend **KSh 10 million**.

They fund their lending account through:

```text
DCP Bank Account
       │
       │ KSh 10M
       ▼
Payment/Bank Integration
       │
       ▼
Platform Ledger
       │
       ▼
DCP Available Lending Balance
```

Now:

```text
DCP Available
KSh 10,000,000
```

The platform knows:

> This DCP has KSh 10M available to fund loans.

The actual money remains with the relevant regulated financial/payment institution according to the DCP's setup.

# 15. One more thing: don't let the "wallet" become a hidden bank

This is especially important for a Kenyan lending platform.

I'd architect it so the platform is primarily providing:

**loan management + payment orchestration + ledger + reconciliation + workflow infrastructure**

while actual money movement happens through appropriately configured external financial/payment accounts and providers.

CBK's current regulatory framework for DCPs is centered on licensing, governance, lending practices, consumer protection, credit information sharing and AML/CFT; the 2025 draft non-deposit-taking credit-provider regulations also emphasize maintaining accurate financial records and customer transaction information. ([Central Bank of Kenya][2])

So I'd make the internal "wallet" a **controlled ledger/settlement representation**, not an assumption that your platform itself is a deposit-taking institution.
